# 兼容性笔记

> 一个插件"在我这儿能跑，在别人电脑上报错"，除了 Node / DSH 版本这些硬条件，
> 最常见的原因其实是**插件组合不同**。下面是这个假设在我们自己屋里能验证的部分。

## 假设：别人的插件会拖累我

按可能性排序，一个插件可能被"别的插件"弄坏的几种方式：

| # | 方式 | 表现 | 我们的处境 |
|---|---|---|---|
| 1 | **工具名撞车** | 后注册的覆盖先注册的，或注册直接报错 | 十个工具都带 `sense_` 前缀，撞车概率低 |
| 2 | **patch 行 id 撞车** | 同名 id 的行互相覆盖，装了 A 却跑了 B | 统一 `sensorium-` 前缀 |
| 3 | **服务依赖** | 依赖某个服务，提供它的插件没装 → 启动失败 | 只 `inject: ['tools']`，不声明任何自家服务 |
| 4 | **全局副作用** | 别人改了工具策略、系统提示、会话事件 | 我们只读 `agent/inbox/claimed`，只 `setInterval`，不改全局 |
| 5 | **状态目录争用** | 两个 agent 用同一个 workspace，状态互相覆盖 | 真实风险，见下 |
| 6 | **别的插件重写 patch** | 装/卸/升级时整体改写 `cordis.patch.yml`，丢掉手写行 | 真实风险，见下 |
| 7 | **版本门** | Node 或 DSH 太老，API 不存在 | `engines.node >= 20`，`engines.dsh >= 0.2.0 < 0.4.0-0` |

## 我们做过的隔离测试（2026-10-24）

把 profile 的第三方 bundle 全部摘掉，只留：

```
@deepseek-ai/dsh-base
@deepseek-ai/dsh-web-app
@deepseek-ai/dsh-experimental-auto-review
dsh-ops          ← 留着是因为要用手边的命令工具做恢复
dsh-sensorium
```

结果：装配行数 **221 → 213**，十个感官仍然全部 `active`，工具正常返回，状态文件照常写。
再把那几个 bundle 加回去，行数回到 221，一切照旧。

结论：**在这个宿主里，感官不依赖任何第三方插件**。但顺序反过来——第三方插件依赖我们、
或两个插件抢同一个 id/工具名——不是这次能测出来的，得靠上表那几条自查。

## 使用者自查清单

装完发现某个感官不工作，按这个顺序看：

1. **它活着吗**：`plugin_manager` 的 `list_plugins`，找 `sensorium-*` 那十行，看 `enabled` 和 `fiberPhase` 是不是 `active`。
2. **id 撞了吗**：`cordis.patch.yml` 里搜 `sensorium-`，确认每个 id 只出现一次。
3. **工具名撞了吗**：搜自己装的其他插件有没有注册 `sense_*`。
4. **写到哪了**：看 `<workspace>/.dsh/sensory/` 有没有文件；没有的话多半是 `workspace` 没配，落到了 `process.cwd()`（在 DSH 里常常是 profile 目录）。
   > 0.0.1 起会在 console 里喊一句：`[sensorium] workspace 落到了 profile 目录……`
5. **时间在走吗**：`pulse_samples.json` 的 `mtime` 应该在每 2 分钟内变一次；`need_tension.json` 每 5 分钟。
6. **patch 被改写了吗**：升级别的插件之后再看一眼 `cordis.patch.yml`，那十行还在不在。装之前备份这个文件。

## 已知的真实风险

- **共用 workspace**：两个 agent 指向同一个 ws，十个状态文件会被互相覆盖。建议一个 agent 一个 ws。
- **patch 文件是单一真相**：任何"安装/卸载/升级插件"的操作都可能重写它。社区插件的管理工具一般会保留未知行，但没人能保证。备份比祈祷便宜。
- **`process.cwd()` 兜底**：从桌面图标的宿主进程，cwd 可能是应用目录或 profile 目录。生产环境请显式配 `workspace`。
